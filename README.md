# Кандидатогенерация для поиска услуг Авито

Задача: по поисковому запросу выбрать из корпуса (189 212 объявлений) до 50
кандидатов так, чтобы в них попало объявление, которое пользователь в итоге выбрал.
Метрика - Recall@50.

Решение устроено как маленький каскад:

1. Для каждого запроса собираем ~600 кандидатов из нескольких источников: BM25 по
   полям объявления, три дообученных нейросетевых энкодера (e5), история выборов
   по похожим запросам из train. BM25 и энкодеры запускаются дважды: с учётом
   локации поиска и без неё.
2. Кандидатов переранжирует LightGBM (LambdaRank) по ~60 признакам, в ответ идут
   50 лучших.

Итог на локальной валидации (устроенной максимально близко к бенчмарку, см. ниже):
Recall@50 = **0.919**.

## Данные и признаки

Из train используется всё: пары «запрос → выбранное объявление» идут на обучение
энкодеров, а сами выборы - как история (что выбирали по такому же или похожему
запросу, где искали и где в итоге выбрали). Для валидации из train отложены
17 500 поисковых групп, они в историю и в обучение энкодеров не попадают.

Признаки пары (запрос, кандидат):

| группа | признаки | зачем |
|---|---|---|
| текст, BM25 | скоры по заголовку, параметрам и описанию, их сумма, доля слов запроса, найденных в заголовке и вообще в объявлении, совпадение фильтров поиска («Вид услуги ...») с параметрами объявления, символьные 3-4-граммы заголовка | точное совпадение слов, опечатки, слитное написание («автоподбор» / «подбор авто») |
| энкодеры | косинус для каждой из трёх моделей, он же с поправкой на локацию, разница с лучшим кандидатом запроса, ранги | смысловая близость, когда слова не совпадают |
| локация | log P(локация объявления \| локация поиска) по истории, та же ли локация, расстояние до центра локации поиска | 83% выборов в train - в локации поиска, но есть «регионы» и соседние города |
| история | сколько раз объявление выбирали по похожим запросам (kNN по эмбеддингам запросов), по точно такому же тексту, по нему же в этой локации; насколько подкатегория объявления типична для похожих запросов | 37% запросов бенчмарка встречаются в train |
| объявление | рейтинг, число отзывов, цена, длина описания и заголовка, скрыт ли телефон, запрещены ли сообщения | при прочих равных выбирают более «живые» объявления |
| запрос | число слов, длина, есть ли фильтры, встречался ли текст в истории, насколько «локальна» локация поиска, сколько в ней объявлений | чтобы ранкер по-разному вёл себя на разных типах запросов |
| источник | из каких списков пришёл кандидат | |

Сознательно не используются категория объявления и популярность объявления в
истории (почему - в разделе про ошибки).

## Модели и алгоритмы

* **BM25** по трём полям с разными параметрами, стемминг Snowball (PyStemmer), в
  заголовке дополнительно биграммы соседних слов. Скор пачки запросов считается
  одним разреженным умножением матриц.
* **Энкодеры** - `intfloat/multilingual-e5-small` и `multilingual-e5-base`,
  дообученные на ~228k пар из train (не больше 30 пар на текст запроса, чтобы не
  переучиться на «маникюр» и «массаж»). Loss InfoNCE с негативами из батча; вторые
  версии моделей учатся ещё и с трудными негативами: похожие по первой модели
  объявления из той же локации, которые по этому запросу не выбирали. В финале
  три модели: e5-small и e5-base с трудными негативами и обычная e5-base.
* **Априор локации**: P(локация объявления | локация поиска) по истории переходов
  со сглаживанием. Жёстко по локации не фильтруем - 17% выборов в других локациях.
* **История**: kNN по эмбеддингам уникальных текстов запросов из train, от соседей
  (косинус не ниже 0.8) берутся выбранные ими объявления и распределение подкатегорий.
* **Ранкер**: LightGBM LambdaRank, 63 листа, lr 0.05, ранняя остановка; финальная
  модель - три сида, ранги усредняются.
* Для запросов с `search_category = 0` («все категории») до 5 последних мест
  отдаются самым близким объявлениям не из категории услуг.

## Как проверялось качество

**Схема валидации.** Тексты запросов в бенчмарке уникальны, и 37.0% из них есть в
train. Если выбирать из train уникальные тексты равномерно и брать для каждого
одну поисковую группу, получается 37.5%, то есть бенчмарк, по всей видимости,
собран так же. Так и сделано: 7 фолдов по 2500 групп, их строки убраны из train.
Выбранные в этих группах объявления добавлены в корпус, но каждое видно только
запросам своего фолда (для бенчмарка их нет).

**Конкуренты.** Оказалось, что у запроса бенчмарка в его локации в 2-3 раза больше
похожих объявлений, чем у того же запроса в случайной локации (например, 18
кинологов и зоопсихологов в Калининграде под «зоопсихолог с выездом»). Видимо, в
корпус попали объявления, показанные по этим запросам. У валидационных запросов
такого окружения нет, и без поправки валидация слишком лёгкая. Поэтому для каждого
валидационного запроса в корпус добавлены копии похожих объявлений из других
городов, перенесённые в его локацию, в том количестве, в каком «лишние» похожие
объявления встречаются у запросов бенчмарка (`src/s03c_competitors.py`).

**Процедура.** Ранкер учится на фолдах 0-5 без отчётного, ранняя остановка по фолду
6, отчётные фолды 0 и 1. Все решения (признаки, модели, параметры) принимались по
этой валидации, разницу меньше ~0.3 п.п. считал шумом.

| что | Recall@50 |
|---|---|
| BM25 + локация (фолд 0) | 0.767 |
| e5-base дообученная + локация (фолд 0) | 0.828 |
| e5-base с трудными негативами + локация (фолд 0) | 0.837 |
| среднее трёх энкодеров + локация (фолд 0) | 0.840 |
| **ранкер, фолды 0 / 1** | **0.925 / 0.912** |

Покрытие кандидатов (есть ли выбранное объявление среди ~600) - 97.8-98.6% по фолдам.
Без конкурентов та же схема давала ~0.96.

## Ошибки, найденные при анализе, и что с ними сделано

1. **Валидация была слишком оптимистичной** (~0.96): в корпусе бенчмарка у запросов
   гораздо больше конкурентов. Добавил симуляцию конкурентов. Ранкер, обученный с
   ними, на трудной валидации оказался лучше обученного без них на 2.2 п.п. (0.929
   против 0.907 на промежуточной версии), то есть поправка влияет не только на
   оценку, но и на само обучение.
2. **Ранкер узнавал копии-конкуренты по артефактам.** Сначала координаты копий
   брались как центр города плюс шум, а признаки истории у копий обнулялись, и
   ранкер научился отличать копии по расстоянию и истории. Исправил: координаты
   берутся у реального объявления той же локации, признаки истории наследуются от
   оригинала. Валидация честно упала с 0.929 до 0.916.
3. **Отбор конкурентов собственными энкодерами** делал валидацию предвзятой против
   этих же энкодеров. Теперь похожесть считается исходной e5-base без дообучения.
4. **Популярность объявления в истории.** В валидации выбранные объявления взяты из
   того же периода, что и история, и 38% из них встречаются в ней (в корпусе в
   целом - 9%). На бенчмарке этот признак может работать иначе, а без него валидация
   теряет всего 0.3 п.п., поэтому он убран.
5. **Запросы «во всех категориях».** У 9% запросов бенчмарка `search_category = 0`,
   в train таких почти нет, и выбирали там только услуги. При этом ~1.9k объявлений
   корпуса не из услуг, и 40% из них ближе всего именно к таким запросам. Категория
   убрана из признаков, чтобы ранкер не выучил «не услуга = не подходит», а таким
   запросам отдаются последние 5 мест (позиции 46-50 на валидации дают меньше 1%
   попаданий).
6. **Региональные поиски и выборы в другой локации** - самое слабое место:
   Recall@50 около 0.83 против 0.94 для обычных поисков, и теряются такие объявления
   именно на ранжировании (в кандидатах их 94-96%). Пробовал признаки «насколько для
   похожих запросов типичны дальние выборы» и флаги «онлайн / доставка» - на двух
   фолдах не помогло, в итог не вошли.
7. Также не помогли: признаки «относительно других кандидатов запроса» (отзывы,
   цена, рейтинг), objective binary и rank_xendcg вместо LambdaRank, другое число
   листьев и learning rate.
8. Технические мелочи: pyarrow до версии 20 не читает `benchmark_queries.parquet`,
   поэтому всё читается через polars; порядок строк в join и unique у polars
   фиксируется явно, от него зависят биграммы и воспроизводимость.

## Воспроизведение

Нужны Python 3.12 и видеокарта с CUDA (проверялось на RTX 3070 Laptop 8 ГБ, 16 ГБ
RAM). Данные положить в `data/` (`train.parquet`, `benchmark_queries.parquet`,
`benchmark_items.parquet`).

```bash
python -m venv .venv
.venv/bin/pip install torch==2.6.0 --index-url https://download.pytorch.org/whl/cu124
.venv/bin/pip install -r requirements.txt
```

**Точное воспроизведение `answer.csv`** - с весами дообученных энкодеров, они
лежат в релизе [weights-v1](https://github.com/Brekinilya/avito-candgen/releases/tag/weights-v1)
(fp16, ~1.2 ГБ; эмбеддинги с ними те же, что при расчёте ответа):

```bash
mkdir -p work && cd work
for m in dense_e5s_hn dense_e5b dense_e5b_hn; do
  curl -LO https://github.com/Brekinilya/avito-candgen/releases/download/weights-v1/$m.zip
  unzip -q $m.zip
done
cd ../src
python s01_prepare.py
python s02_build_bm25.py
python s03_train_dense.py --name e5b_raw --base intfloat/multilingual-e5-base --encode_only
python s03_train_dense.py --name e5s_hn --encode_only
python s03_train_dense.py --name e5b --encode_only
python s03_train_dense.py --name e5b_hn --encode_only
python s03c_competitors.py
python s04_candidates.py
python s05_ranker.py
python check_answer.py
```

Около часа. Сиды зафиксированы, LightGBM работает в детерминированном режиме;
повторный прогон даёт побайтно тот же файл, sha256 `answer.csv`:
`cdf833449c47c6bdc688dca634624516b474f95edaac076aade3dc38f915b320`.

**С нуля, с обучением энкодеров** (около 4 часов на такой карте):

```bash
cd src
python s01_prepare.py
python s02_build_bm25.py
python s03_train_dense.py --name e5s
python s03b_mine_hardneg.py --model e5s
python s03_train_dense.py --name e5s_hn --batch 128 --hardneg ../work/hardneg_e5s.parquet
python s03_train_dense.py --name e5b --base intfloat/multilingual-e5-base --batch 160 --lr 3e-5
python s03b_mine_hardneg.py --model e5b
python s03_train_dense.py --name e5b_hn --base intfloat/multilingual-e5-base --batch 112 --lr 3e-5 --hardneg ../work/hardneg_e5b.parquet
python s03_train_dense.py --name e5b_raw --base intfloat/multilingual-e5-base --encode_only
python s03c_competitors.py
python s04_candidates.py
python s05_ranker.py
```

Обучение на GPU в fp16 не побитово детерминировано, поэтому так получится очень
близкий, но не обязательно идентичный ответ.

## Структура

```
src/
  common.py               пути, чтение данных, токенизация
  s01_prepare.py          валидационные фолды, история, общий корпус
  bm25.py                 BM25-индекс
  s02_build_bm25.py
  dense.py                энкодер: тексты, обучение, кодирование
  s03_train_dense.py      дообучение энкодера и эмбеддинги
  s03b_mine_hardneg.py    трудные негативы
  s03c_competitors.py     конкуренты для валидации
  location.py             априор локаций, расстояния
  history.py              история выборов, kNN по запросам
  s04_candidates.py       кандидаты и признаки
  s05_ranker.py           LightGBM, валидация, answer.csv
  check_answer.py         проверка формата ответа
  export_weights.py       сохранение весов энкодеров в fp16
answer.csv                отправленный ответ
```

## Open-source

Модели `intfloat/multilingual-e5-small` и `intfloat/multilingual-e5-base` (MIT,
HuggingFace), библиотеки PyTorch, transformers, LightGBM, scikit-learn, PyStemmer,
polars, numpy, scipy. Внешние API не используются, всё работает локально.
